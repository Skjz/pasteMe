# 0008 文本子类型不是新的类型，代码的语言也存在同一列

日期：2026-10-18

颜色、时间戳、hexdump、hex、Base64（#26）和代码的语言（#28）都作为文本子类型存在 `clips.text_subtype` 一列里（`base64`、`code:swift`），条目的类型仍然是文本。类型决定卡片怎么展示、粘贴时写回哪些 pasteboard 类型，而这些内容粘贴时和普通文本完全一样；按「文本」筛选时也应该看到它们。子类型由内容推导，识别规则会改，和「类型」这种复制时就确定的事实不是一回事。代码的语言和子类型互斥（一段文字不会既是 Base64 又是 Swift），所以共用一列，筛选「代码」时用 `LIKE 'code:%'`。

## Considered Options

- 每种子类型加一个类型（`ClipKind.color`、`.timestamp`、`.code`…）：卡片的分支更直接，但粘贴、拖出、预览、编辑、去重的哈希、「文本」筛选都要把这些类型当成文本再处理一遍；识别规则改了，已有条目的类型也要跟着改，等于改动复制下来的事实。
- 子类型和代码语言各一列：可以同时表达「Base64 并且是某种语言」，但实际上不会出现，查询和迁移要多管一列。

## Consequences

- 识别规则改了以后，已有条目的子类型不会自动更新。需要重算时加一级迁移，把 `text_subtype` 设回 NULL，启动后的分批补算（`ClipStore.backfillTextSubtypes`）会重新识别。
- `CodeLanguage.rawValue` 存进了数据库，改名要迁移。
- 以后要让某种子类型粘贴时写回别的 pasteboard 类型（例如颜色写成 `NSColor`），就到了该把它升格为类型的时候。
